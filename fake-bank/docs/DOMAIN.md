# Domain

## Purpose

This document defines the minimal payment domain model for Fake-bank v0.1. It describes provider-side payment state, lifecycle semantics, card simulation concepts, and persistence ownership boundaries.

The domain model defines provider-side payment semantics. API handlers, checkout screens,
webhook delivery behavior, scenario execution logic, migrations, and repositories must
respect these domain boundaries.

## Domain Boundary

Fake-bank owns provider-side payment simulation state only.

The domain model includes:

- payment records
- payment lifecycle state
- checkout references
- selected simulator scenarios
- lifecycle history
- scenario state
- webhook delivery records

The domain model does not include merchant-side business state, buyer identity, inventory, fulfillment, accounting, real card processing, or real financial operations.

## Payment Entity

The `Payment` entity represents a provider-side payment record.

### Fields

`payment_id`

Stable provider-side payment identifier. It is generated by Fake-bank and is the primary identifier used to retrieve and update provider-side payment state.

`merchant_id`

Identifier supplied by the integrating merchant application. Fake-bank stores it as a reference value and does not interpret merchant business meaning.

`merchant_reference`

Optional merchant-supplied reference for matching merchant-side records during tests. It is not the primary payment identity inside Fake-bank.

`amount`

Positive numeric payment amount. The domain stores the amount as part of the provider-side payment state used for display, lifecycle records, and webhook payloads.

`currency`

Three-letter uppercase currency code used for display and integration tests. Fake-bank does not apply currency conversion rules.

`payment_method`

Payment method selected for the payment. Fake-bank v0.1 supports `card` only.

`status`

Current payment lifecycle state. Supported values are `created`, `pending`, `succeeded`, and `failed`.

`checkout_url`

Hosted checkout reference returned to the merchant. It points to the buyer-facing payment page for this payment.

`return_url`

Merchant-supplied URL that can be used after buyer checkout completes. Fake-bank stores it as a reference value.

`webhook_url`

Merchant-supplied URL used by webhook delivery behavior. Fake-bank stores it as a provider-side delivery target.

`scenario`

Optional selected simulator scenario. The scenario reference is stored on the payment so scenario execution can produce deterministic outcomes.

`metadata`

Optional merchant-defined string metadata for tests. Fake-bank stores it without assigning domain meaning.

`created_at`

Timestamp when Fake-bank created the payment record.

`updated_at`

Timestamp when Fake-bank last changed provider-side payment state.

### Ownership

`Payment` owns only provider-side payment state. It must not store unrelated merchant operations, buyer account data, product information, shipping state, bookkeeping entries, or real card data.

## Payment Lifecycle

The v0.1 lifecycle is intentionally small and deterministic.

```text
created
    |
    v
pending
    |
    +--> succeeded
    |
    +--> failed
```

### States

`created`

The payment record exists in Fake-bank. It has a provider-side identity and the initial payment data supplied by the merchant.

`pending`

The payment is active and not terminal. Buyer checkout can still produce a simulated outcome, or a selected scenario can keep the payment non-terminal.

`succeeded`

The payment reached a successful terminal state in the simulator.

`failed`

The payment reached a failed terminal state in the simulator.

### Allowed Transitions

- `created` -> `pending`
- `pending` -> `succeeded`
- `pending` -> `failed`

### Terminal States

`succeeded` and `failed` are terminal states. A terminal payment cannot move to any other state.

### Invalid Transitions

The following transitions are invalid:

- `created` -> `succeeded`
- `created` -> `failed`
- `pending` -> `created`
- `succeeded` -> `created`
- `succeeded` -> `pending`
- `succeeded` -> `failed`
- `failed` -> `created`
- `failed` -> `pending`
- `failed` -> `succeeded`

### Transition Rules

Lifecycle transitions must be deterministic. Fake-bank must not use random outcomes to move payment state.

Scenario execution controls simulated outcomes while the lifecycle rules define valid
state transitions.

## Card Payment Model

Fake-bank v0.1 supports one payment method: `card`.

The card model is simulation-only. It does not process real cards, does not validate real card networks, and does not store real payment card data.

### Test Card Concept

Test cards are predefined input values that trigger deterministic simulator behavior. They exist to let developers test successful, declined, and invalid card flows.

### Card Input Structure

Card confirmation input contains:

- `number`
- `expiry`
- `cvv`

The input is used only for simulation. It must not be persisted as real card data.

### Supported Test Cards

`4242424242424242`

Successful test card. It represents a simulated card approval and can move a pending payment to `succeeded`.

`4000000000000002`

Declined test card. It represents a simulated card decline and can move a pending payment to `failed`.

### Invalid Card Behavior

Any unsupported card number is invalid for v0.1 simulation. Invalid card input must not
create a successful or failed provider outcome.

## Persistence Boundary

Persistence stores simulator-owned state required to provide deterministic payment behavior and delivery tracking.

This phase defines persistence boundaries only. It does not create database migrations, repository interfaces, storage adapters, or query behavior.

## Persistence Entities

### Payments

Stores the current provider-side payment state.

Owned data:

- payment identity
- merchant reference values
- amount and currency
- payment method
- current status
- checkout reference
- return and webhook references
- scenario reference
- metadata
- timestamps

### Payment Lifecycle Events

Stores immutable records of provider-side payment state changes.

Owned data:

- lifecycle record identity
- payment identity
- previous status
- next status
- reason
- timestamp

Lifecycle history exists to support traceability and deterministic debugging. It must reflect domain transitions and must not invent states outside the lifecycle.

### Scenario Execution State

Stores simulator scenario progress for payments.

Owned data:

- scenario state identity
- payment identity
- selected scenario
- current scenario step
- scheduled timing reference
- completion marker
- timestamps

Scenario execution uses this state to track deterministic scenario progress.

### Webhook Delivery Attempts

Stores webhook delivery attempt records.

Owned data:

- delivery attempt identity
- payment identity
- event name
- target URL
- payload reference
- attempt number
- delivery status
- response summary
- timestamps

Webhook delivery uses this state to track delivery attempts and outcomes.

## Contract Relationship

The public API contract remains `openapi/openapi.yaml`. Domain changes that affect public request or response semantics must update the OpenAPI contract before implementation changes are made.
